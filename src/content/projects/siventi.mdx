> **SIVENTI** (Sistem Informasi Inventaris & Peminjaman Barang) is a web-based inventory and asset loan management system. We built this as a Project-Based Learning (PBL) initiative for the Department of Information Technology (JTI).

---

### Executive Summary & Role

As part of a 6-person development team, I helped build SIVENTI to digitalize and automate how our department handles asset tracking, borrowing submissions, and approvals. 

Before this, everything was done manually with paper logs and messy spreadsheets. _(seriously, paper logs in an IT department?)_ We wanted to create a platform that actually makes life easier for both students borrowing equipment and the admins managing it. 

We ended up with a dual-portal system: an e-commerce-style catalog for users and a powerful dashboard for administrators to track stock, approve loans, and monitor overdue items.

---

### Key Features

- **Interactive Item Selection:** Users can browse the catalog, add items to a cart, and set quantities based on real-time stock availability. _Just like online shopping!_
- **Automated Stock & Lifecycle Sync:** Stock counts update automatically across the database when admins approve loans or process returns.
- **Borrowing Quotas & Overdue Guards:** Built-in safeguards prevent users from hoarding equipment and automatically flag overdue loans as `Terlambat`.
- **Role-Based Portals:** Completely separate experiences for general users and department administrators, securely routed and authenticated.
- **Central Audit History:** A global transaction log for admins to track every piece of equipment and who borrowed it.

---

### The Problem & The Solution

**The Problem:**
- **Messy Paperwork:** Relying on physical logbooks meant slow approvals and high chances of losing records.
- **No Real-Time Visibility:** Students would come to borrow something only to find out it was already taken or broken. Such a waste of time.
- **Lost Equipment:** Without automated tracking, it was super hard to monitor return deadlines, leading to missing or overdue assets.
- **Data Errors:** Manual spreadsheets made it way too easy to accidentally delete active records or mess up stock counts.

**The Solution:**
- **Centralized Web App:** Built a dedicated portal for users to request items and admins to manage them.
- **Cart-Like Experience:** Users can just pick what they need, adjust quantities, and checkout—just like shopping online, but for campus gear.
- **Smart Safeguards:** We added referential integrity and deletion guards. You can't just delete an item if someone is currently using it.
- **Automated Tracking:** The system handles the math. It knows exactly how many items are available, borrowed, or under maintenance at any given second.

### Technical Details & Architecture

Here is why we chose the technologies we used:
- **Custom MVC Architecture**: We built this using a native PHP MVC architecture from scratch. No heavy frameworks like Laravel, just pure PHP 7.x/8.x with Object-Oriented Programming.
- **MySQL / MariaDB**: For a solid relational database with a normalized schema and prepared statements to keep things secure.
- **Vanilla Tech Stack**: HTML5, CSS3, JavaScript (ES6+), and jQuery. We used custom CSS and AJAX to make the cart feel snappy.
- **Native State Management**: Relied on PHP Sessions, Cookies, and `localStorage` to keep the user's cart intact.

> - **why Custom MVC?** We wanted to truly understand how routing, models, and controllers work under the hood before jumping into magic frameworks.
> - **why jQuery?** It was what we knew best at the time for handling quick DOM manipulations and AJAX requests without the complexity of modern JS frameworks.

---

### Challenges & Learnings

Well this was one of my first major collaborative web projects, so we faced some challenges along the way, such as:
- **Building Custom MVC**: Creating an MVC framework from scratch was a bit challenging. It forced us to really understand routing, sanitizing URLs, and enforcing role-based route guards.
- **State and Cart Logic**: Managing the cart state with cookies and syncing it with real-time database stock limits required some serious logic juggling. _(so many edge cases!)_
- **Database Integrity**: Learning how to properly structure relational databases and use views/constraints so users can't break the system by deleting active loans.
- **Team Collaboration**: Working in a 6-person team on a single codebase meant we had to get really good at dividing tasks, communicating, and managing code merges. _Git conflicts, anyone?_
